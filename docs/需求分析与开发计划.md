## 1 题目究竟要交付什么

交付一个可运行的多账号 Telegram 群组操作平台。操作员连接服务账号、创建群和管理成员、查看可靠消息时间线、启动定时话术序列；Agent 通过受限工具读取消息、回复和移除成员。网页上能看到状态、失败原因和执行过程。

真正的难点是：**外部请求结果不确定、重复乱序事件、多实例并发，以及任意时刻重启后继续执行**。只有页面和正常流程能跑通，尚不能算完成题目。

| 优先级 | 题目范围 | 通俗理解与完成标准 |
|---|---|---|
| A0 | 基础与权限 | 迁移可重复执行；库版本落后时应用拒绝启动；统一错误格式；admin 可写、viewer 后端也必须拒绝写入；access token 15 分钟有效 |
| A1 | 账号状态机 | 严格执行六状态转移表；并发 CAS；终态、移出成员、取消排队消息与关联序列处理必须原子生效；限流截止时间重启不丢 |
| A2 | 可靠网关接入 | 先有数据库出站记录，再调用网关；202 只表示受理；504 先查询对账，确认未发才能重发；重复事件不重复入库或触发 Agent |
| A3 | 异步建群 | 建群、取邀请链接、加入、等待真实成员确认、提升管理员；job 可查失败步骤；创建者成功后直接入成员表，不等不存在的 joined 事件 |
| A4 | 消息与实时推送 | 一条出站消息从 queued 到最终状态只占一行；按 sentAt 展示并稳定分页；WebSocket 先认证，事件序号有序 |
| A5 | 可恢复 Agent | 四个固定工具、严格协议校验、审计、幂等、步数和时间预算；同群最多一个 running；重启延续同一 runId，已发生效果不重复执行 |
| A6 | 前三个页面 | 登录、账号列表、群详情；成员角色、消息状态和最近 Agent 运行可见 |
| B1 | 定时序列及页面 | 变量逐步覆盖与来源追踪；全量预检；前一步真正发送后才安排下一步；并发启动互斥；重启不补发一整串 |
| B2 | 群生命周期 | 邀请链接未就绪/过期/已入群处理；退群时群主最后，其他账号失败则保留群主；最终成员表对账 |
| B3 | 登录会话 | HttpOnly refresh cookie、原子轮换、旧 refresh 重放撤销整个会话、logout 立即生效、前端并发 401 只刷新一次 |
| B4 | 断线与运行详情 | 重连后三秒内补齐前端断线事件且无重复；Agent 每步入参、结果、审计与协议错误可查 |
| C1–C3 | 明确选做 | 媒体文件生命周期、真实 LLM 独立服务（本次按用户确认改为 DeepSeek/OpenAI 兼容接口）、Playwright 端到端测试 |

**B 组属于第二优先级，只有 C 组被题目明确标为选做。** 截止时间不足时可以说明未完成的 B 项，但不能把它们解释为题目没有要求。

不扩入本次范围：多租户/组织树、订阅计费、账号销售、直播功能、国际化、主题切换、响应式、多平台 IM。JD 提到的业务背景不等于笔试要实现这些功能。

## 2 Telegram 实现边界

建议保留题目规定的两个外部服务边界：

```text
React 18 控制台
        │ REST + WebSocket
Go 业务服务 ───────── PostgreSQL
        │                 状态、消息、任务、Agent 步骤、事件
        ├── HTTP + SSE → Telegram 网关
        │                   ├── gotd + Session → 真实 Telegram
        │                   └── fake → 可控时序和故障
        └── HTTP → Agent 服务
                            ├── scripted → 确定性协议测试
                            └── DeepSeek / OpenAI-compatible → C2
```

真实 Telegram 是交付主线，fake 是验证工具。两种模式使用相同业务 DTO 和网关契约，正常账号与群流程在真实 Telegram 上验证；精确的重复、乱序、504/503、审计失败和崩溃窗口由 fake 验证。

实施采用 backend 与 gateway 两个 Go module，隔离 gotd 编译与依赖；Agent 服务位于 backend/cmd/agent。数据库使用同一 PostgreSQL 实例，各模块明确表的所有权。React 壳从 go_tg_assistant 提取。无需额外引入 Redis、Celery、Consul、RabbitMQ 或通用工作流框架。

### Session 和账号安排

- 首轮只支持实际提供的 Session 格式，避免先做通用账号导入中心。
- 现有代码支持 gotd JSON、Telethon `.session` SQLite 转换、tdata 目录/ZIP 转换。没有找到 Telethon StringSession 的现成支持；若实际提供此格式，需要另做转换适配。
- 建议三份服务账号 Session：群主、被提升的管理员、普通成员。另用一个受控测试用户发入站消息并作为踢人目标，可以手工操作，不必成为第四个受管服务账号。
- 首轮优先使用测试超级群，统一 peer/access_hash 和管理权限处理；普通群兼容以后按题目验收需要再加。
- Session、API ID/hash 和代理配置走本地配置/受保护存储，仓库只放示例。一次只让一个受控客户端实例拥有测试 Session，避免原项目和新项目同时争用。

### 真实协议与题目协议的差异

1. Telegram `random_id` 用于防止同一平台发送重复。真实 adapter 应持久保存单次平台操作的 random_id 和回执映射；fake 必须保留“同一 clientMsgId 调两次仍会发两条”的题设行为，不能用网关偷偷去重掩盖业务层错误。[Telegram 发送接口](https://core.telegram.org/method/messages.sendMessage)
2. Telegram 更新恢复依赖 pts/seq 等状态和差量补拉，题目 SSE 的 eventId 则由自建网关持久化事件日志生成。两层游标不能混用，也不能只保存 Session 就认为消息恢复已经完成。[Telegram 更新恢复](https://core.telegram.org/api/updates)
3. Telegram 不承诺题设中的 1–2 秒收敛、毫秒级消息时间戳或账号停用后自动退出所有群。真实模式必须如实记录平台结果和差异，精确时序与终态场景由合同测试覆盖；不能伪造平台确认来让演示变绿。
4. `kick` 应明确是移除还是永久封禁，并使用正确的 peer/access_hash；不能直接复制一个缺实体访问参数的旧调用。

## 4 必须补齐的关键能力

### 账号状态和事务边界

所有来源统一进入状态转换服务，包括手动操作、网关错误和 SSE 事件。CAS 校验与状态保存、终态移出成员、取消 queued 消息、跳过相关序列步骤、记录待推事件必须在同一事务。前端只收到已提交状态。

`rateLimitedUntil` 存 PostgreSQL；限流期间同账号不再调用 send，队列保持原顺序，到期后重新检查状态，避免把已经离线或终态的账号恢复为 online。`GROUP_WRITE_FORBIDDEN` 只改变群和相关运行，不能污染账号状态。

账号退出群或进入终态后仍保留 accountId 与 platformUserId 的身份对应，保证之后补投的历史消息仍能正确标记 isOwn。

### 出站记录和结果对账

手工发送、序列与 Agent 共用一个发送入口。发送前持久化消息与 attempt，202 变 accepted，收到回执才变 sent；迟到的 202 不能把 sent 降级。`message` 和 `message_sent` 无论先后，合并成一行。

504 进入 unknown；在题设 2 秒收敛窗口后查询确认未发，才允许同 clientMsgId 重发一次。查询 503 时保持 unknown，恢复后按题目要求及时收敛，不能把查询失败当未发送。恢复时先对账未决请求，不能直接把 processing 全部改回 queued。

现有 follow_live [发送路径](D:/web_projects/card_code_workspace/go_follow_live/backend/internal/worker/sender.go:382)先发送后标 sent，重试又会生成 RandomID；只能参考平台调用，不能沿用其可靠性结论。

### 入站恢复和实时事件

增加持久 inbox、去重键、安全 SSE checkpoint 和事务 outbox。先保存事件再处理，处理失败可重试；数据库不可用时不推进安全游标，恢复后从网关历史补拉。写库失败的 inconsistency 需有独立可达的告警路径，不能只尝试写入同一个故障数据库。

乱序事件不能简单以最大已见 eventId 推进 checkpoint；采用保守回放边界和事件去重。离线旧消息可能晚任意时长到达，不能按 sentAt 丢弃。服务启动立即订阅事件，不等待账号 connect。

现有 follow_live [监听配置](D:/web_projects/card_code_workspace/go_follow_live/backend/internal/online/manager.go:199)明确接受断线丢消息；[monitor](D:/web_projects/card_code_workspace/go_follow_live/backend/internal/worker/monitor.go:288)还有满队列丢弃。因此这里必须替换为可靠路径。

WebSocket 事件来自持久日志，auth 后补发再接实时流，前端按 seq 去重。设计序号分配和发布顺序时处理事务提交先后颠倒，不能仅靠 BIGSERIAL 和最大已见 seq。

### 稳定时间线分页

不能仅用 OFFSET，也不能只用 sentAt。采用稳定消息身份和确定性二级排序；分页会话冻结成员与排序依据，游标携带快照标识和位置。queued 的 sentAt 后续变更、任意时间旧消息补投，需要通过实时合并/刷新进入当前视图，不能破坏已经开始的“加载更早”。实现前用同毫秒、补投旧消息、queued 改 sentAt 三类用例固定语义。

### 持久 Agent 执行器

必须新增 run、steps、历史、待处理触发消息、审计阶段和工具效果记录。数据库约束保证同群至多一个 running；领取租约与可恢复阶段处理多实例执行。SKIP LOCKED 适合领取队列，但自身不提供完整的外部副作用防重保证。[PostgreSQL 锁定说明](https://www.postgresql.org/docs/current/sql-select.html)

- 四个 tools 名字和 required 入参精确匹配；每次响应必须恰好一个块。真实供应商响应需要 adapter 收敛到题目 envelope，不能原样透传。DeepSeek 思考模式的工具轮次必须保留 reasoning_content 供后续请求使用，不能把它当作用户可见文本。[OpenAI 工具协议](https://developers.openai.com/api/docs/guides/function-calling)、[DeepSeek 思考与工具调用](https://api-docs.deepseek.com/guides/thinking_mode/)
- 每次 turn 往返计一步，最多 12 步；运行累计 60 秒，不计停机；单轮建议配置 12 秒超时；连续三次协议错误结束，合法响应清零；迟到响应丢弃。
- 审计先于 send/kick，最多三次尝试，失败或无结论时不执行效果；全无结论则 blocked，并让页面明确显示。
- `(runId,idempotency_key)` 查重先于重复审计；被审计/策略拒绝的 key 不占用。重复 tool_use.id 是协议错误，不能混同业务幂等键。
- 发消息效果关联统一 outbound；kick 保存意图并在未知结果时查成员列表，重启不盲踢第二次。
- `send_message` 工具最多等待五秒，确认 accepted/sent 后返回；仍不确定返回 SEND_TIMEOUT，并保留原消息继续对账。群不可达、账号失败和无可用账号分别返回题目约定错误，不能统一吞成成功。
- `get_recent_messages` 包含 run 中新消息，最多 50 条；单条 500 字，tool_result 总计 8KB 按字节限制；rawResponse 最多 2KB，摘要最多 200 字。
- 群不可达或关闭 Agent 时在当前步结束后取消；run 结束与下一批待处理消息交接需原子化，避免最后一瞬间到达的消息遗漏。

### 群任务和定时序列

建群/退群存步骤和结果。join 的 202 不等于入群；10 秒无确认记 JOIN_TIMEOUT，promote 总调用不超过两次。B2 要覆盖邀请等待、链接刷新一次、已入群成功，以及非群主失败后群主保留。

序列预检必须完成所有步骤的变量合并，空字符串和来源按题目定义；失败不创建 running。实际发送复用同一解析器与快照，避免预览和发送不一致。下一步按前一步 message_sent 的确认时点排期；恢复只重排最早过期一步；限流顺延而不是 skipped。

### 会话和五个页面

新增 PostgreSQL session 与 refresh 使用记录；轮换事务保留旧 token 对应的会话归属，重放时撤销整会话；access token 带 session id，认证时检查撤销状态以支持立即登出。前端只保留 access token，refresh 不进入 JavaScript 存储。

五个页面按原题交付。群详情内提供必要发送/开关/退群操作，账号合法按钮按状态显示，viewer 隐藏写按钮且服务端拒绝写。Agent 详情和序列预检是新增页面，不能用原项目任务日志页替代。

## 6 以 24 小时内交付为目标

内部目标是从实际开发启动时刻 T0 起，争取 24 小时内完成 A+B、真实 Telegram Session 主流程和 C3 的可验收版本。题目原有 48 小时仍是从收到题目计算的外部截止时间；不能因为重新排期而延长。若外部剩余时间少于 24 小时，以更早的截止时间为准。

这一目标依赖 Session、API 配置、可用网络和 PostgreSQL 能及时就绪。24 小时是压缩后的交付目标，不代表模型档位可以保证全部工程工作按时完成；遇到偏差按下方检查点立即处理。

### 三条并行工作线

固定共享契约后最多同时安排三名员工，每条线只写自己负责的目录。主控维护接口决策、共享契约和组合验收，不成为同一目录的第二写者。

| 工作线 | 责任 | 起步时的验收接口 |
|---|---|---|
| Telegram 网关 | Session 转换、gotd 生命周期、真实群操作、HTTP/SSE 网关、可控故障模式及契约测试 | 固定 accounts/groups/events DTO、错误码、发送回执与成员查询语义；不改业务域表 |
| Go 业务后端 | 迁移、认证、状态事务、inbox/outbox、发送对账、持久 Agent、序列、异步 job、WS 补齐 | 固定 REST/WS 契约与数据库所有权；手工/Agent/序列共用发送能力；先做最小垂直闭环再补场景 |
| React 与端到端 | 五个页面、请求与刷新单飞、消息/Agent/序列状态展示、Playwright | 依据契约样例与 stub 开发，业务 API 可用即接真实联调；不等全部后端结束才开始 |

第一小时明确账号状态表、消息/Agent/序列 DTO、错误格式、网关事件和最小 schema，以及 outbound 执行阶段、inbox/outbox、领取租约和工具效果记录的所有权。测试场景和数据库迁移随模块一起提交。前三条线直接按复制批次开始适配，网关线负责真实/fake 共用的网关契约测试，前端线兼顾页面端到端场景，减轻域后端验证负担。

最晚第 4 小时验证跨三线链路：真实 Session 收消息→网关事件→业务数据库→WS→群详情。Session 验证同时检查目标群权限、收发事件映射与重连恢复；后续持续集成，禁止三线分别开发到最后才合并。第 4–10 小时就执行发送崩溃与事件恢复检查，恢复机制不能后补。

Go 业务后端是主要串行瓶颈。网关线或前端线提前完成时，只能在明确交接、旧写者停止该目录工作后，接手已经分离的 B 项或测试任务；不能为了增加人数而同时修改核心状态/发送模块。

### 模型与执行方式

- 主控保持用户已选择的 GPT-6 Astra / Ultra / Fast，负责架构决策、依赖消解、关键证据和最终验收。
- 员工上限 GPT-6.1 Sol / Ultra。状态一致性、发送对账、Agent 恢复等复杂实现可显式绑定 Sol / Ultra；已固定契约的页面与普通适配按实际难度使用 Sol / Medium 或 High。Ultra 是允许使用的上限，不要求所有查询和微改都使用最高档。
- 原生员工执行档若固定为 Medium/High，不把岗位名称当作 Ultra 已生效。需要 Ultra 时使用支持显式模型/强度参数的执行方式，带上岗位合同，并记录真实运行 ID 与请求设置。
- Fast 独立于 reasoning effort；主控 Fast 已由用户开启，员工 Fast 以可核验的实际运行设置为准，不假定自动继承，不修改全局配置。
- 复用前一轮源码调查和未失效的测试证据；优先一次派发完成一个模块，避免重复扫描、频繁接力和无关全量测试。相关边界变更或测试失败时再扩大验证。

### 偏差处理与范围控制

- 第 4 小时真实 Session 或最小端到端链路仍未连通，立即报告具体阻塞和替代推进路径；fake 工作可继续，真实验收项仍保持未完成。
- 第 10 小时消息可靠性主链未稳定，立即停止 C1/C2 和界面装饰，集中解决影响 Agent/序列的发送与事件问题。
- 第 16 小时应有可集成候选。出现落后时收敛导入格式和非必要组件，不增加人员反复改核心契约。
- 第 20 小时起冻结新增范围，集中处理阻塞、恢复验证与交付。C2 只在 A+B+C3 与真实路径已稳定且不侵占验证缓冲时追加，C1 更后置。
- 不为赶时间省略 CAS、发送防重、权限、审计或崩溃恢复验证。B 项若最终未完成，完成矩阵必须如实标明，不能把按钮存在视为完成。

## 7 验收清单

| 检查 | 必须看到的证据 |
|---|---|
| S1 受理与发出 | 202 后 accepted，回执后 sent；回执先于 HTTP 响应也不降级 |
| S2/S3 重复与自身回流 | 相同事件多投不增加消息行；自身回流 isOwn=true，不产生 Agent run |
| S4 限流 | 截止前网关 send 调用次数不增加；重启后仍等待，随后按账号顺序发送 |
| S5 504 与重复 key | 504 后 1.5 秒落地，同 key 第二次返回现状；网关只有一条消息、审计没有重做 |
| 504 未发与 503 查询 | 确认未发只重发一次；查询故障时保持 unknown，恢复后按约定收敛 |
| S6 协议与审计 | 坏 JSON、未知工具、重复 tool id、超时均可查；三次无审计结论 blocked 且零效果 |
| S7/S8 序列 | 两实例并发只有一个 201；未解变量的 422 包含 stepIndex/key，网关零发送 |
| CAS 与终态 | 并发竞争只有一个成功；取消消息、成员移除、序列处理与状态同事务；重复终态事件不打断消费 |
| 群生命周期 | join 等确认、邀请失效处理、管理员最终角色正确；失败退群时群主保留且两侧成员一致 |
| 任意时点重启 | 在意图落库后、效果完成后但回写前、审计通过后、工具结果写入前分别终止进程并恢复；不靠优雅退出证明崩溃恢复 |
| 分页与补齐 | 同毫秒消息、旧消息迟到、sentAt 变更不导致分页重复/遗漏；WS 重连三秒内补齐 |
| B3 | viewer 直接调用写 API 为 403；refresh 重放后新旧会话凭据均失效；logout 后旧 access 立即失效；并发 401 只刷新一次 |
| 真实 Telegram | Session 连接→建群→两个成员加入→提升→收发→Agent 回复→受控踢人→群主最后退；每步记录平台确认与应用状态 |

真实测试只使用本次指定的测试账号、测试群和受控成员。先验证 `autoKickEnabled=false` 的拒绝，再在明确测试目标上打开；封号、会话过期、FloodWait 等异常用 fake 注入，不通过伤害真实账号来制造。

证据统一关联 requestId、jobId、runId、clientMsgId、eventId/seq。记录模式是 real 还是 fake，以及代码版本；真实功能通过和合同故障通过分别列出，不能互相替代。

## 8 实施前需要明确的协议边界

这些不改变已确认的 Go/Telegram 选择，主要用于防止过度承诺恢复保证：

1. **非幂等外部调用的崩溃窗口。** 题目只明确规定收到 504 后两秒的发送收敛；“请求已送出但进程在收到响应前崩溃”是否有同样的收敛保证并未写明。建群接口也没有请求幂等键或按请求查询接口。实现应保存意图、恢复先对账、无法确认时不盲重试，并在 README 写清所用模拟器假设；不要仅凭 outbox 就宣称任意外部服务下严格 exactly-once。
2. **DB 不可用时的 inconsistency。** 需要区分暂时不能落业务行与数据库整体离线。整体离线时要通过仍可达的实时告警/日志通知并保留恢复线索，恢复后补存；不能把一次失败日志当作事件已可靠处理。
3. **真实 Telegram 与精确时序。** 默认保留原题精确合同测试。真实平台模式另列收敛耗时和不能强制的行为，不能把外部延迟改写成测试通过。如果出题方有新的 Telegram 专用验收规则，再据其调整。
