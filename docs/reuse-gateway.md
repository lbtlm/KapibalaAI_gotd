Necessary new code supplies this examination's public HTTP/SSE envelopes, deterministic fault controls and delayed effects, PostgreSQL state/event persistence, SDK update-state storage, group/role mapping, the standalone entrypoint and the bounded private probe. The source application has no section-2.1 simulator or this independent gateway database model, so copying its HTTP/business handlers would introduce unrelated features and credentials.

No `.git`, production `.env`, source logs, database backups or original Sessions were copied from this source repository. The controller separately prepared user-authorized isolated test sessions under ignored `.local/telegram`; only those files were opened for live checks. Source AGENTS rules were read before source exploration; the source had no CodeGraph index. Once the controller indexed this repository, subsequent gateway understanding/edits called CodeGraph first.

G3 retains the copied send and participant operations and the existing intent/event/snapshot responsibilities. The existing membership merge is extracted into `applyMembers` so history reconciliation can fetch participants outside the global service lock and apply the same event rules under the lock. Necessary additions are limited to persisted-send reconciliation, a public gotd difference ingestion barrier, leased checkpoint writes, bounded too-long recovery, and keyed kick receipts. The adapter now constructs its SDK API/handler/storage as one account binding; the previous direct unguarded checkpoint path and inline handler construction are replaced. There is no SDK fork or general recovery framework.

Pinned SDK exposure was verified in `telegram/updates/state_channel.go` and `state.go` of gotd v0.112.0: difference handling may log a handler error and subsequently store a cursor; channel difference can enqueue other updates asynchronously. The API wrapper commits those payloads before returning the difference, while the shared failure gate rejects later state writes. Ordinary SDK live handlers use the same durable handler and failure gate. `PostgresStore.ExecFenced` reuses the existing fixed lease connection and ownership check for all cursor/access-hash writes; ordinary pool writes are removed from `updateStorage`.

Send recovery relies specifically on [Telegram's random-ID behavior](https://core.telegram.org/api/updates): retain the same account, peer and random ID for the same logical operation across MTProto sessions; completed repeats return the original message, while an in-flight duplicate may remain ambiguous. [messages.sendMessage](https://core.telegram.org/method/messages.sendMessage) defines the request field. The same document requires exact `channels.getMessages` IDs for very old channel gaps. Unavailable/deleted content and historical membership changes are reported as limits. Kick receipts offer durable completed-result replay, but Telegram has no equivalent operation ID for a kick accepted before the gateway saves its result; that window stays unknown and fail-closed.

G4 reuses the existing exact-ID recovery, group snapshot and SDK account pipeline for initialization. It adds only an optional per-account verified-prefix field to the existing group record, and a `Run` boundary used by both production Connect and real gotd Manager regressions. The old hash-only row interpretation is replaced: positive pts denotes a checkpoint, while the same table continues storing access hashes independently. SDK readiness now uses its public `OnStart` callback. There is no second recovery object, history archive or provider/backend change. Same-account incomplete recovery is updated in place on metadata failure; committed limitation evidence persists even if the next top-message target decreases.

G5 adds no new production abstraction or persistence model. The existing startup loop now checks SDK hash presence before its positive-pts shortcut and fills only absent/zero hashes from the registered snapshot. The existing recovery boundary selection now prefers a same-account unfinished committed range over a later ordinary maximum; missing/zero-cursor initialization still uses its verified-prefix rule. The same tests exercise actual gotd startup/subscription/dispatch and the asynchronous history/global-ingest interleaving against PG. Valid SDK hashes and incomplete-recovery limitation records are retained rather than replaced.
