## 真实 Telegram 已验证的范围

- 三份隔离 Session 副本认证成功，并各自加入指定测试群一次；源文件保持原样。
- 两个服务账号通过真实 gateway HTTP 连接。第三个账号保留为外部触发者，尚未连接到业务后端。
- G2 精确发送一条标记消息、一次 POST、零重发。202 受理、唯一发送回执、两个在线服务账号下唯一 own 消息、按 clientMsgId 查询、原 eventId 重连补拉、独占游标无重复，八项检查通过。
- 首次组合尝试发送一条外部触发，Telegram 确认已发送；80 秒内后端入站、Agent run 和回复均为零。脚本关闭 Agent/auto-kick 并保留失败证据。旧 G3 网关后来被动补入该消息，不能把迟到补拉或 G2 own 回执当作正常实时入站通过。
- G4 修复 hash-only/零 pts 初始化后，三个账号均取得有效频道游标；网关从有证明的连续 exact-ID 边界核对历史，缺乏旧证据时从 ID1 开始。不可取得的旧内容与历史成员状态限制明确记录为 recovered_with_limits。Agent 全程关闭，原触发消息在后端唯一、非 own，且无 pending/run。
- 2026-10-15 第二次独立组合实测使用新的证据文件和 clientMsgId，仅一次 POST、无重发：一条入站、一个 Agent run、一条审计 pass 且 sent 的 own 回复，最终 finished/final，附三秒无重复运行观察。启用窗口至验证关闭约 12 秒；Agent/auto-kick 最终均关闭。浏览器实际页面显示回复、已完成运行和关闭的策略。
- public run API 不直接暴露触发消息 ID；本次关联依据是独占窗口内精确消息 ID、唯一新增 run 和无其他入站，明确属于窗口证据推断。原始证据仅保存在忽略的 `.local/acceptance/combined-live-first-failed.json`、`combined-live-second-attempt.json`、`gateway-g4-live-recovery.json`。
- G5 固定提交 92cae90 的二进制随后在两个真实网关实例上执行无发送重启验收：四服务健康、三账号恢复连接、正 pts 和有效 SDK hash，原三条后端消息与唯一 run 保持不变，Agent/auto-kick 关闭且无待处理任务。没有为此再发送消息；两个特殊恢复故障窗口由实际 SDK + PG 的脚本化传输测试验证。
- 未把 fake 故障测试当作真实 Telegram 证据。指定真实群未执行建群、提升、成员移除、退群或真实平台故障窗口强杀；这些正常/故障契约由相应自动化覆盖，不由正常实时闭环推断。
